# Product Decision Log

This log captures choices established in the planning conversation and technical recommendations for the implementing developer. Update it when implementation or product review changes an assumption.

## Established product direction

| ID | Decision | Reason |
| --- | --- | --- |
| DEC-001 | Operate locally and offline after installation | The user's workflow must not depend on a connection or cloud service |
| DEC-002 | Do not require an AI model in the first release | Use parsing, editable rules, and human review |
| DEC-003 | Represent work as a typed graph | Shared systems span scenarios and have dependencies and evidence |
| DEC-004 | Use a Jira-inspired Kanban interface | The user requested a familiar ticket and board presentation |
| DEC-005 | Support Art, Dev, and combined tasks | The same requirement can need both disciplines |
| DEC-006 | Preserve source details and media alongside simplified tasks | A developer or artist must be able to verify the original requirement |
| DEC-007 | Keep subtasks and shared requirements | Large systems need smaller work items without duplicated shared tickets |
| DEC-008 | Separate impact from urgency | Core importance and time pressure are different decisions |
| DEC-009 | Support multiple projects | Later briefs should fit the same workflow and remain isolated |
| DEC-010 | The assistant acts as advisor and reviewer | Current work is briefs, product review, and suggestions |
| DEC-011 | Add optional AI-assisted task suggestions after local filtering, approved by the user on 2026-11-03 | Return concise, source-linked drafts for human review; the offline baseline remains available |

## Implementation recommendations

| ID | Recommendation | Reason |
| --- | --- | --- |
| REC-001 | Store typed records and relations in SQLite | Portable local persistence without a dedicated graph database |
| REC-002 | Use a local service and browser interface | Supports HTML processing, local files, media, and durable storage |
| REC-003 | Require review before candidates enter the production board | Rules do not reliably establish semantic meaning |
| REC-004 | Keep Blocked separate from board status | Blocking can occur at several production stages |
| REC-005 | Reserve automatic P0 assignment and numeric weighting for later review | Avoid false precision and unexplained scheduling decisions |
| REC-006 | Store graph relationships now and defer a graph canvas | Relationships are useful before visualization is necessary |
| REC-007 | Preserve manual edits during source and rule reprocessing | Reimport must not erase human decisions |
| REC-008 | Use complete project bundles for backup and transfer | CSV cannot preserve the graph and local assets |

REC-005 means P0 is manual-only in the initial policy. The default P1–P3 mapping is specified in the implementation brief and can change after reviewing actual task results.

## AI integration planning on November 3

The user approved including the AI stage and asked how to use the existing Codex account. The local CLI is version 0.166.0 and reports ChatGPT sign-in. Plan a Codex CLI adapter for this trusted personal application, with a conventional API adapter available later. This is an implementation recommendation, not a completed inference test or a claim about remaining account limits.

Keep one adapter contract, filtered request previews, validated evidence IDs, AI provenance, and a human approval step. Use the [AI integration brief](../Architecture/ai-integration.md) and the AI task group in the [implementation plan](../Tasks/implementation-plan.md). Application code has not been changed to call a model by this planning update.

The optional AI action requires a connection when backed by Codex/OpenAI services. DEC-001 and DEC-002 continue to require the non-AI workflow to function offline. Do not share this account when distributing the application or treat a cached Codex token as an API key.

| IDEC-004 | **Launch**: `app/run.sh` or `python3 -m organizer` from `app/`; binds `127.0.0.1:8765`. | IDEC-005 | **Data directory**: `app/data/` by default, overridable with `--data-dir` or `ORGANIZER_DATA_DIR`. Holds `organizer.db`, `projects/<id>/{sources,assets}`, and `trash/`. | IDEC-006 | **Migrations**: numbered `.sql` files; each runs in one transaction with its version record. | IDEC-007 | **IDs** are random UUID4 hex strings; ticket numbers come from a per-project counter that only moves forward, in the same transaction as the insert | Data model "stable IDs"; "never recycle a deleted ticket number" |

### Interpretations of the data model and board spec (Assumptions)

| ID | Assumption | Where the spec was silent or open |
| --- | --- | --- |
| IDEC-010 | **Ticket prefixes are unique across projects** (2–10 characters, letters and digits, starting with a letter) and cannot change | Spec makes the prefix immutable but does not say two projects may share one. Unique prefixes keep keys like `LOG-12` unambiguous and avoid collisions when bundles are restored |
| IDEC-011 | **Hierarchy**: a child's level must rank strictly below its parent's (epic, then task, then subtask), and a subtask must have a parent. Epics are always top level. Tasks may be top level or under an epic | Spec forbids an epic below a task and a subtask containing a task or epic. A parentless subtask has no meaning, so it is refused. The strict ordering also makes hierarchy cycles impossible; the database repeats the rule in triggers |
| IDEC-012 | **Manual tasks are created already approved** (`review_state = approved`, `provenance = manual`) and start in Backlog. The schema default for other creators is `needs_review` | "An approved candidate starts in Backlog"; manual work has no import review step |
| IDEC-013 | **Priority policy is already active for manual tasks**: on every write the suggestion and its rationale are recomputed from impact and urgency using the brief's default mapping (Critical/High to P1, Medium to P2, Low to P3, High urgency promotes one tier up to P1, Unassessed gives no suggestion, P0 never suggested). A manual override and its reason are stored separately and win for display | Brings forward part of IMP-010 so that impact and urgency are meaningful in M1. The stored fields are exactly those of the data model |
| IDEC-014 | **Field origin**: every change is recorded in `task_field_change` with an origin. The details panel shows "Manually set" only for fields the user actually set; untouched defaults read "Not set" | Data model "store field changes with their origin"; avoids claiming a default was a decision |
| IDEC-015 | **Filter semantics**: a discipline selection is a set of predicates joined by OR (Dev matches Dev-only and combined; Art likewise; Both requires both; Unassigned means no discipline). Different dimensions are ANDed. Priority filters use the effective priority (override, else suggestion); *Not assessed* matches tasks with neither | Spec: Dev includes combined, Both requires both, dimensions AND, values OR |
| IDEC-016 | **Parent shown through children**: a top-level card appears if it or any descendant matches. It appears once and states how many subtasks matched, and its progress notes children hidden by the filter. Progress counts direct children | Spec: "show its parent once with a matching-subtask indicator" |
| IDEC-017 | **Card ordering**: ranks are integers with gaps of 1024 per project and status, rebalanced when a gap runs out. Dragging or Alt+Arrow places a card before a named neighbour. A status change from the menu or details places the card at the **top** of the target column; new tasks go to the **bottom** of their column | Spec requires persistent ordering but not where menu moves land |
| IDEC-018 | **Done with unfinished children**: the service refuses with the list of unfinished descendants until the caller confirms. Children are never changed | Spec: "show the remaining work and allow an explicit decision" |
| IDEC-019 | **Sidebar "Backlog"** is a flat list of every approved task of every level with a status quick-filter (default All), not only tasks in the Backlog column | Spec lists Backlog in the sidebar without defining it. Easy to narrow if the user wants only Backlog-status work |
| IDEC-020 | **Deleting a task** is allowed only when it has no children. Its dependency links, criteria, tags links and history go with it; its number is not reused | Data model invariants; avoids orphaning work |
| IDEC-021 | **Concurrency**: last write wins per field (the UI sends only changed fields). No optimistic locking in M1; writes are serialized by SQLite | One local user. Revisit if two browser tabs editing the same task becomes a problem |
| IDEC-022 | **Dependencies were pulled forward**: add/remove with duplicate, self, cross-project, and cycle rejection, shown in details. Requirement, scenario, and reference links remain in later milestones | Data model invariants and the details panel spec; small cost once hierarchy validation existed. Dependency state never sets or clears Blocked |
| IDEC-023 | **Due date** accepts date-only (`YYYY-MM-DD`) or an ISO date-time and stores it unchanged; the UI only writes date-only values | Data model "preserve date-only values as date-only" |

### Import mechanics

| ID | Decision | Reason and trade-off |
| --- | --- | --- |
| IDEC-024 | **Files are chosen by path, not uploaded by the browser.** The interface asks the local service to list folders (names of folders and `.html` files only) so a person can pick the HTML file and media folder; a terminal command (`python3 -m organizer preview|import`) uses the same pipeline. `--import-root` confines browsing and importing to chosen folders | The sample is 956 MB. A browser upload would copy it twice and cannot reveal absolute paths anyway. Trade-off: the service can list folders on this computer, which is acceptable because it is bound to localhost, checks `Host`/`Origin`, and can be confined |
| IDEC-025 | **Media is copied into content-addressed storage** (`assets/<hash prefix>/<sha256>.<ext>`) in one streaming read that also hashes and sniffs the file. One `asset` row exists per referenced path, so two paths with identical bytes share one stored file (3 of the sample's 61 paths are byte-identical copies, leaving 58 stored files) | Satisfies "hashing" and "managed storage" and keeps re-imports cheap. The original names and relative paths are kept on the asset rows |
| IDEC-026 | **Path validation happens before any file is touched.** A reference is percent-decoded, then refused if it is absolute, contains `..`, backslashes, control characters, or a `file:` address, if any component is a symbolic link, or if it resolves outside the selected media folder. Refused and missing references are kept and reported (`blocked`, `missing`, `unreadable`); they never fail the import | Offline-processing "Local file handling". The media folder, not the HTML file's folder, is the import root |
| IDEC-027 | **One transaction writes everything for a document**, after all files are copied. A run row exists from the start (`running`) so a failed, cancelled, or interrupted attempt stays visible. At start-up leftover `running` rows become `interrupted` and partial copies are swept. Runs are **not resumable**; a retry starts over (already stored files are recognised by hash, not duplicated) | Satisfies "previous valid state or a resumable import run" with the first option. Resumability can be added if imports ever become long |
| IDEC-028 | **Re-importing**: the same HTML with the same media is reported as identical and changes nothing. The same HTML where a missing file is now present attaches that file to the existing document (`asset_refresh`) without touching its content. Different HTML becomes a new **version** of the document (v2, v3…) and the earlier version is kept. There is no merge, diff, or proposal yet | Pipeline step 2 and "reimport identical input must not duplicate". Changed-source proposals are IMP-014, not Milestone 2. **Assumption**: attaching recovered files this way is acceptable instead of a separate "Locate file" action |
| IDEC-029 | **Only one import runs at a time**; it runs in a background thread and reports stage and byte progress; it can be cancelled. The preview step reads and parses but writes nothing | "Import running: show stage and progress without freezing the interface" |

### Parsing and structure

| ID | Decision | Reason and trade-off |
| --- | --- | --- |
| IDEC-030 | **HTML is parsed as data into a tree and walked into ordered blocks** (title, heading, paragraph, list item with depth and parent, table, image, video, audio, attachment, divider, quote, code, callout, toggle). Tables keep rows and cells as `source_cell` rows. Inline formatting and links are kept as small run lists. Column layouts record a group and index so Milestone 3 can respect them. Notion attributes (element ids, figures, attachment links) are used when present; ordinary HTML is handled the same way | "Preserve headings, paragraphs, lists, tables" and "Recognize attachment links as assets". Colspan/rowspan and nested tables are not interpreted |
| IDEC-031 | **The preview is rendered from stored blocks, never from the source markup.** Scripts, styles, frames, forms, SVG, event handlers, `javascript:`/`data:` links and remote images are dropped at parse time and counted in the notes; the interface builds elements from text only, under a Content-Security-Policy that already blocks anything external. Web links stay clickable only on user action and are marked as needing internet; web images are shown as a placeholder | "Parse imported HTML as data. Display sanitized content without executing scripts or automatically fetching external resources" |
| IDEC-032 | **Original wording is evidence and immutable.** Block and cell text cannot be updated after import (database triggers). Only markup is removed; a line break inside a text node becomes a space, and whitespace at the very start or end of a block or cell is trimmed. The original HTML file is also stored unchanged under `sources/` | Data model "Keep original source text immutable". **Assumption**: edge trimming is acceptable (for example identifier `004 ` is stored as `004`) |
| IDEC-033 | **Heading paths come from a heading stack**; each block belongs to a section and carries its path. Page properties (the exported header table) are stored as a `metadata` section, shown, and never used as task data | "Do not infer individual ticket assignees, deadlines, or completion from project-level metadata" |
| IDEC-034 | **Historical sections are detected by heading text, not by sample specifics**: an ordinal such as `1st`, a bracketed date such as `(20/09)`, a history word such as revision/changelog/archive/deprecated (English and Vietnamese), or a version label. Children inherit. The reason is stored and shown. A person can set a section and its subsections to current or historical; that choice is stored as made by the user. Everything undetected is current. Historical content stays viewable and searchable | "Let the user change this interpretation". **Assumption**: the word and pattern lists are a starting vocabulary (OPEN-004) and will miss unusual labels, which is why the change is one click |
| IDEC-035 | **Scenarios** come from a table whose header names an identifier and at least one more known column (`Video No.`/`Concept`/`Scenario` and common synonyms, accent-insensitive). A person can choose another table and columns. Each row keeps the identifier as written, the concept, the cell's full original text, and a preamble. Scenario tables inside historical sections are not extracted until the section is marked current. **Assumption**: scenarios belong to the document that defines them (unique per table row), not to the project, so two briefs that both use `001` do not collide; Milestone 4 will match across versions | Data model `Scenario` has no document link; Milestone 4 needs a stable identity across reimports |
| IDEC-036 | **Inline numbered steps are split only when the pattern is clear**: two or more lines that start with a number and a dot or bracket, with nothing else between them; or a clean 1, 2, 3… sequence on one line. Repeated or skipped numbers are kept in order and noted. Anything else is left unsplit with the original text, and the table row keeps the untouched cell. Step numbers are labels, never keys | "Segment only when the pattern is clear… an unsplit fallback for ambiguous cells" |

### Media and serving

| ID | Decision | Reason and trade-off |
| --- | --- | --- |
| IDEC-037 | **Media is served only through `/api/assets/<id>/file`** with byte-range support (needed to seek in video), an ETag, `nosniff`, a sandboxing policy, and a type taken from the file's content. Only common image, video and audio types are shown inline; SVG and unrecognised types are download-only | "Local media previews should use controlled application routes". SVG can contain script, so it is never rendered |
| IDEC-038 | **Large media loads only on request.** Images and GIFs over 3 MB (11 of the sample's 16 GIFs, the largest 105 MB) show a card with a "Show here" button; video and large files open in a viewer. Thumbnails exist only for small images because there is no image library to make others | Opening a document must not decode hundreds of MB |
| IDEC-039 | **A file's availability is kept with the reference, not discarded**: missing, blocked or unreadable files keep their original path, the reason, and where they are used. To recover one, restore it and import the same brief again (IDEC-028). A dedicated "Locate file" action is not built | UI spec "Missing assets show Locate file, while retaining the original reference"; the recovery action itself is IMP-016 |
| IDEC-040 | **Removing an import is allowed** because nothing references source documents yet. The document rows are deleted, and its stored copy and any media no other row uses are moved to `trash/`, not erased. Milestone 3 must refuse removal while tasks cite the document | A way back from a wrong import |
| IDEC-041 | **Requests that are not saves (previews, starting or cancelling an import) do not use the header's "Not saved" state**; their errors appear where the action was taken | A rejected preview must not look like lost work or block leaving the page |

## Implementation decisions (Milestone 3)

Recorded by the implementing developer on 2026-11-01 after the advisor's [Milestone 2 review](../Reviews/2026-11-01-milestone-2-review.md). Items marked **Assumption** interpret the written requirements and are listed for confirmation. Implemented in [`../../app/`](../../app/README.md); results are in the [Milestone 3 handoff](../Tasks/milestone-3-handoff.md).

| ID | Decision | Reason and trade-off |
| --- | --- | --- |
| IDEC-042 | **Candidates live in their own table, apart from tasks.** A task, and its ticket number, exists only after approval. Candidates carry the proposal (title, kind, parent, reviewed values) and link to source blocks, scenarios, media and rule suggestions. **Assumption**: this replaces the data model's `Task.review_state = needs_review` for generated work | Ticket numbers are never recycled, so unreviewed proposals must not consume them; dismissing 90 candidates should not leave gaps in `HFL-n`. The board already shows only approved tasks, so nothing else changes |
| IDEC-043 | **Grouping is structural and conservative.** A section's own blocks are split into groups by *labels* (short emphasised paragraphs: a highlight colour or all-bold text, at most 60 characters, no "Label: text" shape) and by column layout. A label with actionable lines is a **task**; a label with only pictures (or pictures plus short captions) is an **asset label**; explanatory text and headings such as Goal, Reference, Important, Scenario are **notes**; a list that is mostly quantities (at least four lines, 40 percent or more containing one) is a **configuration list**. Bullets are **requirement lines** under their task, never tasks of their own | Review: labels such as Wood shave are paragraphs, not headings, so a heading-only split would build one oversized ticket. All vocabulary and thresholds are constants at the top of `candidates.py`. **Assumption**: tuned against one real brief, so expect some wrong guesses (for example *1st floor (Core)* becomes a task); each is one click to dismiss or retype |
| IDEC-044 | **Scenario scopes.** A line such as `Scenario 001 + 002 + 005 + 006` opens a scope: the lines that follow carry those scenario identifiers until the next scope. When every scope of a group opens with its own sub-label (`Shave clean wood: …`, `Shave bad wood:`) each scope becomes a **subtask** with its own lines; otherwise the group stays one task and its lines keep their different scenarios. Identifiers the document does not define (a missing `099`) are flagged on the candidate and no link is made | Data model: shared tasks, scenario-specific requirements, nothing copied per scenario. Offline-processing: unresolved identifiers are a deterministic check |
| IDEC-045 | **Negation is preserved.** A line that starts with a negation word (No, Not, Never, Without, Don't, Avoid, Không, Đừng …) is an **exclusion**. Exclusions are never proposed as tasks, never read by rules (so *No build fence animation* cannot produce an animation suggestion), and are approved as exclusion requirements on their task. A line that merely contains "No" later in a sentence stays a requirement, visible in full | Offline-processing "Preserve negation". A person can flip any line between requirement and exclusion |
| IDEC-046 | **Quantities are kept as written** (`10 wood logs`, `50 coins`, `~10-12 seconds`) and shown as chips; nothing is converted, summed or rounded. **Values elsewhere in the document are offered, never attached**: a loose requirement (for example section 3.5's *Wood logs per shave*) is suggested to the top-level task that shares at least two stemmed words with it, with the shared words as the reason; a person attaches it or not | Review: "do not assume nearby text connects every value to every task". Word overlap can mislead, which is why it is only an offer |
| IDEC-047 | **Media suggestions have two sources and three states.** Pictures directly under a label (or sub-label) in the same layout, and pictures of an asset label that shares two or more words with the task (*Handheld wood shaver* for *Wood shave*), are **suggested** with the reason. A person **attaches** or **removes** them; a removed one does not return. Only attached media is copied onto the ticket | Offline-processing "Keep a proposed association distinguishable from a confirmed one" |
| IDEC-048 | **Rules** are phrase lists (`*` at a word end matches endings; whole-word otherwise; case-insensitive by default) looked up in the title, the task's own non-exclusion lines, its heading path, or any of them; operators contains and equals; outputs discipline (Art, Dev, or both), category, impact, urgency. Five global rules are seeded from the offline-processing table plus Vietnamese equivalents and can be edited or turned off; project rules are added in the interface. **Resolution**: disciplines accumulate; for a single-value field a project rule outranks a global rule, then higher precedence wins; equal-ranked rules that disagree are all *Conflicting* and nothing is chosen; a field you already set is never overwritten (its suggestions become *Not used*); accepted and rejected suggestions survive a rerun. **Assumption**: the seeded *Gameplay section* rule reads "Core gameplay heading" as any heading containing "gameplay" | A match explains a suggestion; it never confirms one. No percentages, no scripting |
| IDEC-049 | **Priority stays derived and separate.** A candidate shows the policy's suggestion from its reviewed impact and urgency with the rationale, and a manual override (P0 to P3, with a reason) that is stored separately. P0 is only reachable by override. Approval passes impact, urgency and the override to the same policy the board already uses | IMP-010; brief "P0 requires explicit user selection" |
| IDEC-050 | **Approval is one transaction** and a deliberate act. Selected tasks bring their requirement lines and, by default, their subtask candidates. It creates tickets in Backlog (provenance *source extraction*), requirements (original text, quantities, exclusion flag), links to the exact source blocks, confirmed scenario links for the lines that named scenarios, and the attached media. Rule suggestions that were not accepted and media that was not attached are *not* applied, and the confirmation says so. Field history records a value as *rule* when it came from an accepted suggestion and *manual* when a person set it. A subtask cannot be approved without its parent; notes and asset labels cannot be approved | Brief "approval is a deliberate action"; data model "retain links back to the exact source blocks". The requirement and link tables arrive now because approval must store them; managing links afterwards is IMP-012 |
| IDEC-051 | **Source evidence is protected.** Links from tasks and requirements to source blocks and media have no cascade: a document that approved tasks cite cannot be removed (the message says how many). Deleting a task deletes its requirements and returns its candidates to *dismissed*, so they are not recreated unasked and can be restored and approved again | Review: "prevent source removal from destroying evidence" |
| IDEC-052 | **Generating again only adds.** Each candidate has an identity (heading path, normalised text, ordinal), independent of ids and import version. A candidate that already exists in any state, with its edits, approvals, dismissals and rejected media, is left alone; new groups are added; rule suggestions are recomputed without touching reviewed values. Candidates a person creates (split) have their own identity and are never matched | IMP-014 will match across source versions; stable identity now avoids rework |
| IDEC-053 | **Split and merge.** Split moves chosen lines of a task into a new candidate (beside it or as its subtask); the original label stays as context. Merge previews the kept title, lines, source blocks, media and scenarios, then moves everything into one candidate and leaves the others visible as *merged*; where two candidates set the same single-value field differently, the kept one's value wins and the preview says so. Only unapproved candidates can be split or merged; merging approved tickets is IMP-013 | "Merging must preview … preserve evidence" |
| IDEC-054 | **The listening backlog is raised to 128.** The standard library default of 5 can refuse connections when many requests arrive together | The advisor saw one intermittent `OSError(22)` in a parallel-create test that passed alone; this is the most likely cause, not a proven one |
| IDEC-055 | **Requirement ownership is retained, not guessed (M3 REV 001).** A requirement approved before its parent task is created once and keeps its place in the candidate tree. When the parent is approved, every already-approved child is attached to the new ticket; nothing is duplicated. The approval dialog tells a *child line* (attached later to a named task) from a *shared requirement* (belongs to no task), and the result names lines still waiting for their parent | Review M3 REV 001 allowed either "require approval with the parent" or "retain pending ownership"; the second loses no work |
| IDEC-056 | **Hierarchy edits validate the whole subtree (M3 REV 002/003).** A change of kind or level is checked against the candidate's children as well as its parent: a parent with subtasks cannot become a subtask, and a group with lines or subtasks cannot become a note. Merge requires the same level and re-checks everything that moves; split cannot move a subtask under a new subtask. The interface offers one **Move or change level** dialog that sends level and parent together and lists only valid places | Review M3 REV 002 and 003. The old Level and Parent selectors are removed so no invalid intermediate state can be saved |
| IDEC-057 | **Task-first view.** The default view of a task is title and compact badges, a short editable description, one main reference, and any open question. Subtasks, Details (classification, rule evidence, priority, lines, scenarios), Supporting references and Original source are collapsed; the three-pane source comparison is opt-in (**Compare source**). On the board the editable properties stay visible because they are the management controls; the main clip, question and collapsed evidence are added above and below them | [Task presentation brief](../Design/task-first-review-flow.md). The board panel was not reduced to badges only because status, assignee and dates are edited there |
| IDEC-058 | **Reference roles, one primary, ranges.** Each reference attached to a candidate or task has a role (primary demo, supporting demo, asset reference, source evidence), an editable caption and an optional start/end time in milliseconds. The database allows at most one primary per candidate and per task, requires a primary to be attached, and requires a task's reference to belong to the task's project. Choosing a primary is an explicit click and attaches a suggestion in the same step; clearing demotes it and never deletes a file. A range applies to video only, end needs start, and an unknown range stays empty | Design brief "Data changes". Ranges are stored on the link (not the shared reference) so one video can serve different tasks with different ranges |
| IDEC-059 | **Suggested clips are ranked, not decided.** Tier 0: media inside the task's own lines; tier 1: directly under its group; tier 2: shared wording across sections. At most three of tiers 0 and 1 (one per distinct file) are shown first; everything else is under *More references*. Importer captions that are only file names or upload ids are replaced by a short readable caption such as "GIF animation from 3.4. Gameplay Sequences Sample"; the file name stays in the details | Design brief "Reference selection rules"; the sample's clips are named by hash |
| IDEC-060 | **Open questions are a first-class record.** A question (typed by a person or asked by the AI) belongs to a candidate, optionally cites source blocks, and stays visible until resolved, in the review, in the approval dialog and on the ticket. Editing a description never removes it. No contradiction is detected automatically, because that would hard-code the sample's problems into the parser | Design brief "Do not hide a contradiction"; RawData analysis lists the log conflict as a source question |
| IDEC-061 | **Description history.** Every description that is replaced (by a person, by an AI draft, by a restore) is kept as a version and can be restored | Product brief: "keep the previous version available for recovery" |
| IDEC-062 | **AI provenance is explicit.** Migration 0004 rebuilds `candidate` so `origin` can be `ai` (SQLite cannot alter a CHECK) and adds `ai_run_id`, `ai_draft_id`, `description_origin`. The migration runner supports a `-- migrate: foreign_keys=off` marker: it turns foreign keys off outside the transaction, runs the rebuild, runs `PRAGMA foreign_key_check` before committing, and turns them back on. Tested on a copy of the live database (98 candidates, no violations) | Brief: "the current candidate origin enum must not mislabel AI work". The backup before upgrade is unchanged |
| IDEC-063 | **AI is off until a person turns it on, and drafting is a staged, reviewable flow.** Select → preview exactly what is sent → run in the background → validate → choose what to import → normal approval. The request replaces internal ids with temporary names (b1, r1…), carries no file paths or pictures (captions only), and is limited by configurable block, character and batch limits shown in the preview. Failures never change the project | AI integration brief |
| IDEC-064 | **Codex CLI adapter.** Argument array, `shell=False`, request on stdin, instructions as one argument, `--output-schema` and `--output-last-message`, `--json` events kept separate, a dedicated 0700 temporary working folder removed afterwards, a minimal environment that never passes API keys, `--sandbox read-only`, `--ask-for-approval never`, `--ephemeral`, `--ignore-user-config`, `--ignore-rules`, `mcp_servers={}`, `web_search="disabled"` and every listed feature that gives the model tools switched off (shell, exec, code mode, apps, plugins, hooks, browser, computer use, image generation, memories, view image, multi-agent, goals, skill search). Timeout and cancellation kill the whole process group. Capability and sign-in are checked with `--version`, `login status`, `exec --help` and `features list` | AI brief. A live probe showed the model still lists some built-in tools that this version cannot disable, so this is documented as a **trusted personal pilot**, not isolation |
| IDEC-065 | **AI answers are validated independently of the CLI schema.** Shape, extra or missing fields, enums, lengths, request id, duplicate draft ids, and every source, reference and scenario id against the supplied set; a task must cite evidence and a source-supported subtask must cite a block. Any such failure rejects the whole answer. A number in a draft that is not in its cited text is a per-draft warning and that draft's description is not applied by default | AI brief "Validate ... every ID". Quantities are only checked as digits; units and wording are not verified |
| IDEC-066 | **Importing AI drafts is idempotent and conservative.** A draft goes to the existing candidate whose source lines it overlaps most (or a new candidate). Its description is applied only when the current one is empty, was itself an AI draft, or the person ticks replace; the old text is kept as a version. AI subtasks with the same title as an existing subtask update that one instead of duplicating; others are created as `ai` candidates (inferred ones labelled). Candidate identities derive from parent, title and cited blocks, so importing twice or from a retry run adds nothing. Classification and primary-clip suggestions become proposals; questions become open questions. Everything is one transaction, and a run can only be imported into its own project | AI brief "Preserve manual edits and prevent duplicate imports" |
| IDEC-067 | **Runs belong to their project.** A run stores its project, document, provider, requested and reported model, prompt and schema versions (hash of the packaged text), request format and input hash. The interface tracks runs by id, not by what is on screen: finishing elsewhere shows a notice that names the original project and links back. Only one run is active at a time. A run left running by a stopped service is marked interrupted | AI brief "Keep results attached to their original project" |
| IDEC-068 | **A "description only" draft is deliberately narrow.** *Draft with AI* on one task imports only a description; the bulk action on up to three tasks also brings subtasks, proposals and questions | Product brief: Draft description must not become an instruction to reorganise the project |
